# M1.5：Engineering Hardening

> 状态：已完成（2026-09-04）。该阶段已于 M1 完成后正式加入路线图，不是一次性验证分支。

## 1. 目的

M1 已证明确定性 coding loop 能运行；M1.5 要证明它面对预期故障时不会崩溃、不会丢失可诊断证据，并且核心行为能够稳定回归。

M1.5 是里程碑名称，其中形成的 failure-injection case、semantic golden、replay projection 和真实 fixture 会贯穿后续 M2—M4。后续功能必须扩展这些门禁，而不是弃用它们。

## 2. 边界

本阶段增加：

- Runtime 级权限拒绝、模型非法响应和测试失败恢复场景；
- Tool Harness 未预期异常与测试超时注入；
- 稳定语义 trajectory projection 与 golden comparison；
- replay 的 Token、工具、测试结果和 source invariant 汇总；
- 一个 20—100 行的 `todo-cli` empty-input bugfix demo。

本阶段不增加：

- 通用 Shell 或 OS 级沙箱；
- SQLite checkpoint、interrupt/resume；
- 真实模型 provider；
- 完整 context compression；
- 批量 eval runner 或 LLM judge。

## 3. 失败语义

必须区分三类结果：

| 场景 | Tool status | Runtime state | 说明 |
|---|---|---|---|
| edit 权限被拒绝 | `permission_denied` | 继续产生 observation | Harness 正常工作，模型可解释阻塞或改变策略 |
| 测试断言失败 | `success` + `passed=false` | 继续产生 observation | 测试进程执行成功，但代码质量门禁未通过 |
| 测试基础设施超时 | `timeout` | 继续产生 observation | Harness 终止进程组，模型可决定下一步 |
| backend 响应非法 | 不适用 | `FAILED` | Runtime 无法获得有效决策 |
| FSM 非法迁移/预算耗尽 | 不适用 | `FAILED` | Runtime 自身无法安全继续 |

`COMPLETED` 只表示执行循环正常结束并得到 final answer，不等同于 task success。M3 的 oracle 才负责独立判断任务是否成功。这一边界避免把工具拒绝误报为 Runtime crash。

## 4. Semantic golden

Golden 不保存 UUID、时间戳、绝对路径或 duration，而保存稳定投影：

```json
{
  "schema_version": 1,
  "final_state": "completed",
  "transition_path": ["created->preparing_workspace"],
  "tool_order": ["read_file", "edit_file", "restricted_test"],
  "tool_status_counts": {"success": 3},
  "test_outcomes": [true],
  "metrics": {
    "model_calls": 4,
    "tool_calls": 3,
    "tool_failures": 0,
    "input_tokens": 0,
    "output_tokens": 0,
    "test_runs": 1
  },
  "constraints": {
    "source_unchanged": true,
    "final_test_passed": true
  },
  "failure_kind": null
}
```

四个长期 golden case：

1. `bugfix_success`：标准 read-edit-test-final；
2. `test_failure_recovery`：首次测试失败，二次修改后通过；
3. `permission_denied`：写权限拒绝成为 observation，Runtime 不崩溃；
4. `runtime_failure`：非法 backend response 被分类为 Runtime failure。

- [x] 汇总 input/output tokens。
- [x] 汇总 tool order、按状态失败数和 test run 数。
- [x] 提取最后一次测试是否通过、source invariant 和 failure kind。

- [x] 输出不包含运行时随机字段的 semantic projection。

### Failure injection

- [x] 权限拒绝完整经过 model → tool → observation → final。
- [x] 首次测试失败能被模型观察，继续编辑并重测成功。
- [x] handler 未预期异常被 Harness 转换为结构化 result。
- [x] restricted test timeout 返回 timeout 且不遗留主进程。
- [x] 非法 scripted response 形成分类失败轨迹。

### Golden 与真实 demo

- [x] 建立四份 semantic golden 文件和 comparison tests。
- [x] 增加 `todo-cli` 小仓库，复现 empty input crash。
- [x] scripted run 至少经历一次测试失败再恢复。
- [x] README 记录 task、最终状态、源目录、workspace 和测试结果。

## 6. 验收标准

1. 全量静态检查和测试通过。
2. 四个 golden projection 与运行结果完全一致。
3. 权限拒绝和测试失败不会造成未分类异常或丢失 observation。
4. todo demo 最终 `COMPLETED`，最后一次测试通过，源 fixture fingerprint 不变。
5. replay 指标与 `run_finished` 事件交叉校验一致。
6. Runtime 注册表仍只有三个 M1 工具，且无通用 Shell。
7. M2/M3/M4 路线明确要求继续扩展 failure/golden 门禁。

## 7. 后续继承规则

- M2：增加 checkpoint 崩溃窗口、重复副作用和 provider timeout fault cases。
- M3：增加压缩事实丢失、oracle failure 和 batch runner fault cases。
- M4：增加路径逃逸、资源耗尽、禁网和子进程残留对抗 case。
- Golden schema 需要版本化；升级时迁移 golden，不能删除失败历史来获得绿灯。
